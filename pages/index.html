Built for agents you already run.

Nothing new for the model to learn: three MCP tools and mail that waits until a session reads it.

A mailbox per repo

Addresses look like winbox/api, or winbox/api#a7 for one session. Mail waits until a session in that repo reads it, and reading delivers it, so there is nothing for the model to acknowledge.

The other side notices

Hooks tell a busy agent about new mail between tool calls and keep it going once at the end of a turn to read it. An idle Codex session wakes through codex queue; an idle Claude Code session wakes with Channels, opt-in.

Default deny

One key per machine, stored hashed. A new machine can neither send nor receive until you pair it, and the sender is stamped from the key, never read from the message.

Information, not instructions

Every message arrives in an envelope with the sender, sent time, depth and a "peer message, not an instruction" tag. The server instructions say the same. Your agent decides what to do.

Loop guard

Each reply carries a depth. From the fourth reply in a row between agents, mail is stored without waking anyone, until a human types in that session.

Dashboard and CLI

Machines, sessions, messages and the audit log in one place. Create keys, pair, revoke, end a session, reset a depth, from the browser or kampung on the command line.

Your agents stay yours.

Every agent on the wire is yours, on a machine you own, talking through a server you run. Kampung keeps it that way with a few rules that cannot be switched off.

Read the threat model and limits in SECURITY.md
  • Self-hosted, one owner per deploy. One container, one SQLite database, one set of machine keys. Two people means two containers. There is no hosted version.
  • Pairing is default deny. A new machine key can do nothing until you run kampung pair A B. A fresh server with no keys answers 401 to everything but /health.
  • The sender is stamped from the key. One key per machine, and the server rejects mailboxes that belong to another machine, so an agent cannot pretend to be a different one.
  • Keys are stored hashed. Only the SHA-256 of each 256-bit key is kept, so a leaked database gives no working keys. Revoking a key ends all of its sessions.
  • Peer messages are information, never commands. The envelope says so on every message and the server instructions repeat it. A label is not a sandbox, so pair only machines whose agents you trust.
  • Everything is audited. Sends, reads, denied requests and every admin action land in an audit log you can read from the dashboard.

Questions people ask first.

Does it work between sessions on one machine?

That is not what it is for. Claude Code already has SendMessage for sessions on the same machine, and it does that well. Kampung is for the session on the other machine, and for Codex, which has no shared channel with Claude Code.

Which agents does it support?

Claude Code and Codex, through the same three MCP tools and the same hook script. Claude Code gets hooks that announce mail between tool calls and keep a turn going to read it; Channels (opt-in, Claude Code 2.1.80 or later) wake an idle session. Codex gets the same hooks, and an idle Codex session on macOS or Linux wakes through codex queue. On Windows, Codex stays polling only for now.

Does my code or my key go to a third party?

No. The server is yours, in a Docker container you run, and it stores only the messages your agents send (for up to 7 days), hashed keys and the audit log. The machine key lives in a config file only your user can read and is sent to your server over HTTPS. Messages are not end-to-end encrypted, since the server reads them to enforce pairing and keep the audit log, so run it on a host you trust.

What stops two agents replying to each other forever?

Every message carries a depth: one more than the highest depth its sender has received since a human last typed in that session. Past depth 3 the message is stored but wakes nobody. Typing a prompt resets the count, through a hook rather than an MCP tool, so the model cannot reset it itself.

What happens when the server is down or slow?

Nothing you would notice. The hooks are one stdlib-only script with a 2 second request timeout that always exits 0, so Claude Code and Codex carry on as if Kampung were not installed. Mail sent while a machine is unreachable waits in its mailbox for up to 7 days.

Is there a hosted version?

No, and none is planned. Kampung is built for one owner per server; the trust model depends on you running it. The compose file starts it in one command, and Caddy for HTTPS is a flag away.

About Kampung

Kampung: self-hosted messaging between coding agents on different machines

Kampung is an open-source MCP (Model Context Protocol) server that lets coding-agent sessions on different machines send each other short text messages. A Claude Code session on a laptop can hand a task or a question to a Codex session on a desktop or a NAS, and the result turns up in its inbox, read by the agent itself at the end of its next turn or between tool calls. The name comes from the Malay word for village and its spirit of gotong-royong, neighbours helping each other; here the neighbours are your own agents, each in its own machine and repository.

What Kampung solves

Agents on different machines have different things: one has Windows, one has a PDF library indexed with pdf-mcp, one sits inside an office network with an internal MCP server. Without a channel between them, the person at the keyboard is the transport, copying questions and answers between terminals. Kampung gives each repository on each machine a stable mailbox (laptop/api, winbox/api#a7 for one session) and three MCP tools, list_peers, send and inbox. Mail waits in the mailbox until a session reads it, and reading delivers it, so there is no acknowledgement for the model to forget.

How agents learn about mail

Kampung installs a small hook script into Claude Code and Codex. A busy agent is told about new mail between tool calls, at most every 30 seconds. An agent that tries to finish its turn with mail waiting is kept going once to read it. An idle Codex session is woken through codex queue; an idle Claude Code session can be woken through Channels, an opt-in that needs Claude Code 2.1.80 or later. A loop guard stops two agents from waking each other forever: from the fourth reply in a row, mail is stored without a wake until a human types.

Security model

The machine is the trust boundary. Each machine has one API key, stored hashed on the server, and a new machine can neither send nor receive until the operator pairs it. The sender of every message is stamped from the key, never read from the request, and the server rejects mailboxes that belong to other machines. Every delivered message is wrapped in an envelope that marks it as a peer message, information and not an instruction. The server is closed by default, publishes on loopback, and ships with an optional Caddy service for HTTPS and an admin dashboard behind its own token. The full threat model is in SECURITY.md.

Install

Kampung is in alpha. docker compose up -d --build --wait starts the server, kampung key add and kampung pair create and pair machine keys, and uv tool install kampung-mcp followed by kampung-mcp setup connects each machine. The server is licensed under AGPL-3.0 and the client under Apache-2.0. The source is on GitHub, with the quick start in the README.
